# Finance CLI App Agent Guide

## Project Shape

- `backend/app/` is the FastAPI CFO Platform. Keep routes under `/api/v1`; use the application ports, infrastructure adapters, and `shared/composition.py` container rather than coupling routes directly to implementations.
- `backend/finance_cli/` is the Typer-based quantitative CLI. Preserve deterministic simulation behavior and explicit random seeds.
- `frontend/` is the React/Vite CFO Command Center.
- `backend/tests/` contains backend tests, commonly organized by implementation epic. Frontend unit tests live with source and end-to-end tests live in `frontend/e2e/`.

## Backend Workflow

From the repository root, install development dependencies with `make install`.

- Run a focused backend test with `cd backend && uv run pytest tests/test_<area>.py` before broader checks.
- Run all backend tests with `make backend-test`; run linting with `make backend-lint`; run Pyright typing with `make backend-lint`.
- Start the API with `make backend-dev`.
- For API behavior, use the FastAPI app factory and `build_container()` test pattern rather than module-level mutable application state.

## Frontend Workflow

From `frontend/`, use Node.js 24 and pnpm 10.

- Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, and `pnpm build` for a frontend change. Use root `make e2e` and `make e2e-live` when the user flow is affected.
- After changing a FastAPI route or Pydantic request/response model consumed by the frontend, run `pnpm api:sync` before frontend validation.
- Never hand-edit `frontend/src/generated/`; it is generated by the API synchronization step.
- Use `VITE_API_MODE=mock pnpm dev` only for frontend-only work. MSW fixtures must match the generated contract.

## Cross-Component Rules

- The backend owns finance calculations, authoritative validation, authorization, workflows, and persisted state. The frontend owns presentation, interaction state, formatting, visualization, and accessible loading/empty/error states.
- Do not recreate finance, risk, or simulation calculations in the browser. Do not invent unavailable frontend read models, identity headers, or company/period/scenario data; retain explicit mock/local-context labeling until a backend contract exists.
- Treat the FastAPI OpenAPI schema as the machine-readable frontend/backend contract. Keep generated types, API adapters, MSW handlers, and feature queries aligned.
- Preserve governance, audit, company scope, and model/run lineage whenever changing a backend domain workflow.

## GitHub Project workflow

- [Finance CLI App Project #2](https://github.com/users/Timeless90/projects/2) is the source of truth for tasks, priorities and delivery status in `Timeless90/finance-cli-app`. Read [the project workflow](docs/development/github-project-workflow.md) at task intake.
- Tim sets priorities and authorizes implementation. `Ready` requires his authorization and clear acceptance criteria/dependencies; a board change never starts autonomous work by itself.
- Read the issue and its project status before work. For a new request, find or create the corresponding issue without duplicates and add it to the project. Explicit implementation instructions from Tim can authorize that task; record the authorization rather than asking again.
- Maintain issue progress, blockers, actual validation evidence and PR links for authorized work. Move through `Backlog`, `Ready`, `In progress`, `In review`, `Done`. Code work is Done only after acceptance criteria and merge; non-code work after documented acceptance.
- GitHub CLI (`gh`) is supported for issues and Projects when the connector lacks the required operation. Missing access must be reported; never claim an external update succeeded without verifying it.
- Roadmaps describe intent and architecture, not a second live backlog. Existing local/unpublished work and historical test evidence must be labelled accurately. Preserve unrelated edits and existing branch/commit/push/PR approval rules.
